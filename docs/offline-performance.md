# 방치 정산 성능 점검 (2026-09-07)

현재 캐시 소유와 입력 설명은 2026-10-06 main `4fd7c494`와 대조했다. 아래 측정 표는 당시 합성 실험의 기록이다.

방치 효율 10~30%, 인정 시간 3~24시간을 유지한다. 효율을 낮추거나 이동·공격 횟수를 줄여
시간을 맞추는 실험은 제거했다. 현재 구현은 실제 전투를 100ms 단위로 실행하며 공격 순서,
회복, 드랍 추첨, 필수 선택에서 정지, 저장 실패 롤백을 유지한다.

## 계산 간소화

- 표시하지 않는 능력치 툴팁 설명은 생성하지 않는다. `breakdowns`만 null이며 화면 조회에서는 생성한다.
- 같은 능력치 계산에서 해석한 장비 옵션과 젬 입력을 후속 계산에도 전달한다.
- 격리된 정산 상태에서는 장비 옵션·젬 추가 레벨 등 정적 빌드 입력을 재사용한다.
  처치·사망·레벨·지역/루프·장비·패시브·보상 목록이 바뀌면 캐시를 갱신한다.
  처치 처리 종료 후에도 캐시를 비운다. 제거된 생장판 기하는 현재 캐시 대상이 아니다.
- 최종 능력치 전체는 보관하지 않는다. 생명력과 버프 생성·만료 등 동적 상태는 매 틱 계산한다.
- 같은 종류의 여러 소환수가 한 갱신에서 젬 레벨 계산을 공유한다. 관통 계산에는 필요한
  필드만 전달하며 매 타격마다 거대한 능력치 객체를 복사하지 않는다.
- 지원 브라우저의 `scheduler.yield()`로 중첩 타이머 대기를 피한다. 미지원 환경은
  기존 타이머를 사용한다. 진행률 DOM은 정수 퍼센트 변경 시 갱신한다.

`data/build-stat-inputs.js`는 공유 빌드 입력, `js/background-build-cache.js`는 방치 캐시와 공용 빌드 서명을 소유한다.
`getBackgroundBuildMemo`의 WeakMap은 정산 스냅샷을 키로 사용하며 저장 데이터에 포함되지 않는다.
이 방치 캐시는 포그라운드 계산에 적용하지 않는다. 공용 빌드 서명은 장비 분석·요구조건 검사에서도 사용한다.
정산 중 사용자 입력은 원본 상태를 보며 복제된 빌드를 수정하지 않는다.

## 추가 간소화 및 앱 발열 대응

2026-09-07 추가 변경에서는 장비의 기초/추가 옵션 합산·지역 방어 수치까지 정산 스냅샷 안에서
재사용한다. `combat-build-stats.js`는 `combat.js`보다 먼저 로드한다. 합산 버킷은 외부로 반환하거나
열거·직렬화하지 않는 내부 값이며, 캐시를 원형으로 하는 매 평가별 객체에 주얼·키스톤 변환을 쓴다.
따라서 반복 평가에서 방어 전환이나 주얼 효과가 중첩되지 않는다. 도감 대상 목록은 정적 데이터에서
한 번 만들고, 스탯 합산의 긴 분기문은 기존 버킷 shape와 복합 옵션 목록을 조회하도록 정리했다.

동일한 60초 전투의 결과 해시는 계속 일치한다. 24시간 전체 정산은 추가 변경 후 53.18초였다.
이번 측정은 프로파일 수집을 끈 값이므로 앞의 68.43초와 정확한 개선율로 비교하지 않는다.
10초 목표는 여전히 미달이다. 방치 효율, 전투 틱 간격, 회복·공격·드랍 횟수는 유지한다.

온라인 전투도 수치만 계산하고, 능력치 설명은 화면에서 조회할 때 생성한다. 모바일 전장 렌더는
약 30fps, 캔버스 배율 최대 1.5로 제한한다. DOM 메뉴와 글자 해상도는 바꾸지 않는다.
Android 비활성 이벤트는 WebView의 visibilitychange보다 먼저 와도 전투·렌더를 멈춘다.
청크 정산은 UI가 넘긴 일시정지 콜백을 확인하고 비활성 동안 쉬었다가 같은 시뮬레이션을 재개한다.
실물 휴대폰이 연결돼 있지 않아 온도·전력 감소량을 측정한 결과는 아니다.

## 사용자가 선택하는 정산 가속

기본 정산의 효율과 100ms 전투 규칙은 그대로다. 정산 창에서 가속을 누를 때마다 아직 계산하지
않은 유효 전투 시간을 절반으로 줄인다. 2·4·8·16배는 남은 작업량을 줄이는 단계이며, 기기에서
실측한 처리 속도 배수나 보상 배수가 아니다. 뒤늦게 가속해도 이미 계산한 시간과 보상을 깎지 않는다.
100ms 미만의 나머지도 버리며 `skippedMs`로 결과 창에 표시한다. 포기한 시간에는 전투 타이머,
회복, 처치, 보상을 적용하지 않는다. 즉시 종료는 남은 시간을 전부 포기하고 현재 결과만 저장한다.

UI가 `getControl` 콜백으로 선택을 전달하고, 재생기는 청크 사이에서만 이를 적용한다.
공유 게임 상태의 격리·기존 저장 트랜잭션·중복 정산 방지는 유지된다. 저장 실패 시 기존 상태와
방치 스냅샷을 보존하며 재시도할 수 있다. 선택하지 않으면 기존 보상을 포기하지 않는다.

## 앞부분 실측과 나머지 투영 (2026-10-07)

사용자 결정: 정산을 빠르게 하되 "처음 2분에 운 좋게 극도로 희귀한 재화/아이템을 먹었다고 나머지 부분에 모두 복제하는 건 금물".

먼저 고친 버그(3df6a8af): 정산 재생이 탐험 맵에서 멈췄다. 걸음이 끝난 순간 접근을 이어 가는 일을 화면 프레임만 해서, 틱만
도는 재생은 막힌 칸을 사이에 둔 적과 거울처럼 한 칸씩 오갔다(제작 T15 혼돈 20 재생 10분: 16~68마리 → 483~509마리). 이제
`actExplorationProgress.tick`이 걸음이 끝난 20ms 단계에서 이어 간다. 검사: `scripts/smoke-background-exploration-approach.js`.

방식(`js/combat-replay-projection.js`, 규칙 `data/offline-progress.js` `OFFLINE_PROJECTION`):
- 정산 경로(`startBackgroundCombatReturn` → `simulateBackgroundCombatChunked({project:true})`)만 투영한다. 진단용
  `simulateBackgroundCombat`는 끝까지 실제 전투다.
- 실제 전투가 지도 한 바퀴(조우 시작부터 다음 조우 시작, 이동과 사망 포함)씩 기록한다: 무리 종류(보스 단계, 콘텐츠 방, 정예,
  일반)별 전부/일부/안 잡음, 처치한 생명, 물체 사용, 사망, 끝날 때 레벨. 자리를 비울 때 진행 중이던 지도는 재지 않는다.
- 같은 지역의 온전한 바퀴가 셋 이상, 합쳐 3분 이상(첫 투영은 실제 2분 뒤)이면 다음 지도부터 투영한다. 실제 생성기로 새 지도를
  만들고 잰 비율로 무리를 고른다. 처치는 실제 `handleEnemyDeath`(새 난수), 물체는 실제 보상, 사망은 실제 `handlePlayerDefeat`,
  완료는 실제 `finishEncounterRun`이다. 넘어가는 값은 진행 값뿐(바퀴 시간, 무리별 처치율, 물체 사용률, 사망률)이고 재화와 장비는
  없다.
- 보스가 쓰러지는 지도는 정예를 모두 잡는다(보스는 정예가 다 쓰러져야 나온다). 죽는 지도는 보스를 빼고 잰 평균 시간을 그대로
  쓴다. 나머지 지도는 처치한 생명에 맞춰 0.5~2배.
- 레벨이 오르거나 투영 20분마다 실제 바퀴를 하나 더 잰다(실제 전투 합계 10분 안). 속도는 가장 높은 레벨에서 잰 바퀴 위주다.
- 실제 전투로 돌아가는 경우: 다른 지역(밀어붙이기, 운석, 아틀라스 등급), 공허 균열, 입장권 보스, 나무꾼, 지도 완료 뒤 멈춤,
  보스 전 정지 사냥, 이야기 각본 보스(강제 패배, 루프 관문), 액트와 혼돈 깊이와 아틀라스 밖의 지역. 실제 전투 10분을 써도 바퀴를
  다 못 재면 남은 시간도 실제다.
- 결과 창 한 줄: "빠른 계산: 실제로 싸운 N 동안의 속도로 나머지 시간(M)을 계산했습니다. 보상은 처치마다 새로 굴렸습니다."
  진행 카드는 재는 동안 "(전투 속도 재는 중)".

행운 비복사 검사(`scripts/smoke-background-projection.js`): 같은 시드로 두 번 정산하고, 한 번은 실제 전투의 처치마다 황금률 5개를
난수 없이 더 준다. 처치 수, 경험치, 레벨이 같고 황금률 차이는 정확히 실제 처치 수 × 5다.

측정(데스크톱 node, 60분 시드 4개 평균, 실제 전투 2~3개 평균 대비):

## 방치 효율 2 (2026-10-08)

사용자 질문: "3시간만 10%속도로 쳐주는 이유가 계산이 오래걸려서 그런데, 이거 효율 올려줘도 괜찮을까?", 이어서 "효율을 올리는
방법을 더 만들어줘". 리뷰 전체는 docs/late-game-review-20261008.md.

### 고친 것

- **액트는 빠른 계산을 한 번도 타지 않았다.** `isScriptedStoryAct`가 `act.specialType`의 참 거짓만 봤는데 이야기 액트 열 개는
  모두 `'normal'`이다. 각본 보스(`forced_defeat`, `loop_gate`)만 실제 전투로 남긴다. 위 표의 "브라우저, 시작 전사 액트 1 18분"은
  실제로는 투영 없이 잰 값이다. 시작 전사 180분 정산: 97.5초 → 15초대.
- **크는 영웅.** 실제 10분만 재고 속도를 고정하면 루프 초반 54분 정산 처치가 실제의 66%였다(레벨 8에서 15 사이 지도 한 바퀴가
  140초에서 58초로 준다). 이제 레벨이 오를 때마다 실제 전투 30분(`realHoldMs`)까지 다시 재고, 평균은 예전 레벨의 바퀴를 레벨
  차이만큼 절반씩 덜 센다. 주기 재측정(20분마다)은 여전히 10분 예산 안이다. 시드 6개 평균(54분, 시작 전사): 처치 -4.0%,
  경험치 -1.5%, 9초(실제 전투만이면 24초). 제작 T15 432분: 처치 +1.8%, 26초.
- **소환수 빌드가 지도에서 멈췄다.** 싸울 적이 없으면 소환수는 제자리에 선다. 위습 여덟이 3칸 통로를 막아 영웅이 옆방에 갇히면
  정산 내내 처치 0이었다. 영웅의 탐험 걸음은 자기 소환수를 지나가고, 들어선 칸의 소환수는 영웅이 떠난 칸으로 옮긴다
  (`getHeroStepBlockedCells`, `swapSummonOutOfHeroTile`, 검사 `scripts/smoke-hero-walks-through-summons.js`).
- **실제 전투 상한.** 투영을 못 탄 실제 전투가 30분을 넘으면 밀어붙이기를 멈추고 지금 지역을 반복해 투영이 재게 하고(정산 뒤
  플레이어 설정은 되돌린다), 1시간을 넘으면 남은 시간은 계산하지 않는다. 결과 창에 각각 한 줄.
- **후반 측정 장면이 얼어 있었다.** `--endgame` 장면은 전투 틱 없이 만들어 전투 시계가 없었고, 정산은 가짜 떠난 시각부터 시작해
  탐험 지도의 시계보다 하루 늦었다. 영웅이 한 걸음도 걷지 못해 탐험 지도가 생긴 뒤의 후반 측정은 모두 처치 0이었다. 측정
  스크립트가 장면의 전투 시계를 지금으로 둔다(실제 저장은 전투 시계를 갖고 있어 해당 없음).

### 빨라진 것 (결과는 같다)

- `findFreeGridCell`: 지도 전체의 빈 칸을 모아 거리순으로 정렬하던 것을, 한 칸짜리 유닛은 가까운 고리부터 찾는다(무작위 3천 번

## 능력치 계산의 틱 분리 (2026-10-08)

사용자 결정: 정산 중 능력치 재계산을 빌드에서만 나오는 몫과 틱마다 바뀌는 몫으로 나눠 줄이고, 결과가 같은지 그림자 비교로
확인한 뒤 바꾼다("그래 진행해").

### 계측

- 실제 전투 정산에서 능력치 계산 비중: 시작 전사 10분 44%(4.96초 중 2.18초), 후반 소환사 3분 33%.
- 처치 사이에 능력치를 통째로 다시 쓰는 상한 실험(결과는 틀린다): 20분 정산 9.7초에서 4.5초.
- 구간 비중(시작 전사 / 후반 소환사): 버킷 14 / 23%, 젬 출처와 스킬과 능력치 23 / 33%, 생명력부터 막기까지 25 / 19%,
  출력 객체 24 / 10%, 재능 후처리 8 / 3%, 소환수 DPS 추정 3 / 9%.
- 읽기 기록기(game의 최상위 필드에 접근자를 씌운 시험판): 계산은 필드 48개(시작), 56개(후반)를 읽는다. 싸우는 동안 바뀐 것은
  전투 시각, 적, 적 디버프, 순환 버프 상태뿐이고 나머지는 처치나 레벨업 때만 바뀐다.
- 정적 분석(계산이 닿는 함수 469개): 틱 입력은 본문 약 35곳(생명력과 보호막 비율, 전직 키스톤과 고유 아이템의 중첩과 만료
  시각, 살아 있는 적 수, 마지막 피격 시각)과 보조 함수 일곱(정예 특성 버프, 순환 버프, 재능 카드 중첩, 분노 중첩, 원소술사
  과부하, 지역 이동 보너스, 회복 상한)이다. 구역 정보(층, 깊이)는 처치 없이도 바뀐다.

### 나눈 방식

틱 입력이 버킷 단계부터 출력까지 모든 구간에 흩어져 있어서, 단계로 자르면 틱마다 35~40%를 여전히 다시 계산한다. 그래서
입력 종류로 나눴다(`js/player-stat-cache.js`).

- 틱(`playerStatTick`): 시계, 영웅의 생명력과 중첩, 시한 버프, 적을 읽는 식을 계산 본체에서 그대로 옮겼다. 계산은 이 값을
  `tick.get(이름)`으로만 읽고, 읽은 이름과 값이 기록된다. 만료 정리와 마지막 피격 시각 같은 부수 효과는 읽기 함수에 있어서,
  캐시로 답할 때도 그 값을 다시 읽으며 매번 일어난다.
- 캐시(`playerStatCache`): 상태 객체마다 계산을 둔다(설명 없는 것과 있는 것 따로). 빌드 메모 판본, 장비 평가, 구역(`getZone`),
  사용 스킬, 맥락 값(`PLAYER_STAT_CONTEXT_FIELDS`), 세대 번호가 같고 계산이 읽은 틱 값이 모두 같으면 계산을 다시 쓴다. 처치
  처리(`handleEnemyDeath`)와 지도 완료(`finishEncounterRun`)는 빌드 입력(경험치와 젬 레벨, 무기 숙련, 그루터기, 보상, 시련)을
  바꾸므로, 그 안에서는 매번 계산하고 끝나면 세대가 바뀐다.
- 매 호출 끝(`finishPlayerStats`): 새 복사본 위에서 수호자 최후의 저항 정화, 현재 표적에 대한 소환수 DPS 추정, 면역 줄을
  처리한다. 전투 틱이 받은 능력치를 고쳐 쓰기 때문에(조건 버프, 냉각 공속, 스킬 대상 수) 캐시 객체를 그대로 넘기지 않는다.
- 정산 재생 상태와 평소 플레이 상태에서 쓴다(평소 플레이는 아래 "평소 플레이로 넓힘"). 정산이 아닌 상태에 백그라운드 표시만
  켠 경우(검사, 도구)는 빌드를 제자리에서 고칠 수 있으니 매번 계산한다.
- 버려지던 한 줄을 뺐다: 예전 끝부분은 능력치를 다 만든 뒤 충격 추적자의 충격 효과를 보상 버킷에 더했는데, 아무도 읽지 않았다.

### 평소 플레이로 넓힘 (같은 날)

사용자 질문: "지금 변화로 평소에 계산도 빨라진건가?" 처음 분리는 정산에만 캐시를 써서 평소 플레이는 그대로였다(전투 틱의 33~56%가
능력치 계산). 이어서 "문제가 생길 부분까지 다 생각해서 만들어줘. 또 전에꺼랑 나중꺼랑 다 포함해서 앞으로 컨텐츠 추가할 거까지
생각해서" 정산과 평소 플레이를 한 구조로 묶었다.

평소 플레이가 안전한 까닭과 막은 곳:

- 장비 평가는 틱 밖에서 부를 때마다 빌드 서명(`BUILD_STAT_FIELDS`, `BUILD_STAT_PARTS`)을 다시 읽고, 틱 안에서는 틱마다 한 번
  읽는다. 서명이나 장비 칸이 바뀌면 평가 객체가 바뀌고, 캐시 키가 그 객체를 본다. 그래서 입력이 없는 코드 경로(나무꾼 빌드 잠금,
  자동 착용, 장비 비교용 임시 착용)가 빌드를 바꿔도 다음 계산이 바로 맞다.
- 서명 밖 값은 `PLAYER_STAT_CONTEXT_FIELDS`(구역, 층, 시련, 무기 숙련)의 값을 키에 넣는다. 목록에 더하면 키에 저절로 들어간다.
- 플레이어 입력(누르기, 떼기, 클릭, 키, 바꾸기, 놓기)은 처리기가 돌기 전과 다 돈 뒤에 한 번씩 세대를 바꾼다(`js/main.js`).
  확인 창을 거쳐 늦게 적용되는 패시브 찍기도 뒤의 한 번이 덮는다.
- 상태 객체를 통째로 바꾸는 경로(불러오기, 초기화, 클라우드, 장비 비교용 임시 상태)는 새 객체라 처음부터 계산한다.
- 받은 능력치는 겉과 `sSkill`, `breakdowns`를 복사해 넘긴다. 깊은 복사는 시작 전사 정산을 6~8% 늦춰서 하지 않았다. 대신 안쪽
  객체를 고치는 호출자는 검사(넘겨준 계산이 바뀌면 실패)와 아래 자체 점검이 잡는다.
- 자체 점검: 같은 계산으로 64번 답할 때마다(`PLAYER_STAT_SELF_CHECK_ANSWERS`) 새로 계산해 비교한다. 다르면 바로 새 값으로 고치고
  콘솔에 한 번 알린다. 알림 없이 바뀐 입력이 있어도 틀린 값이 오래 가지 않는다.
- 모든 구역 객체(217개)가 JSON으로 바뀌고 가장 큰 것이 547자임을 확인했다. 새 구역이 순환 참조나 큰 데이터를 담으면 검사가 걸린다.
- game 밖 모듈 상태: 계산이 읽는 것은 여섯(고정 데이터 색인 둘, 틱 안 장비 평가, 그루터기와 부적 메모, 시험용 효과 확장 레벨)이다.
  진짜 입력인 시험용 레벨은 바꾸는 함수가 캐시를 버린다(이것을 놓쳐 `smoke-skill-effect-expansion`이 실패한 것을 보고 찾았다).
  새 모듈 상태를 읽으면 정적 검사가 실패한다.
- 체력 비율 키스톤(w7, a6, gd7)과 보호막 비율 키스톤(wlk7): 계산은 체력 값이 아니라 원래 식 그대로의 판정 답을 기록한다
  (`tick.when`). 체력이 경계를 넘을 때만 다시 계산한다. 경계값은 판정하던 때의 값으로 고정한다(뒤에서 최대 생명력이 바뀌어도 그대로).
  체력이 매 틱 바뀌는 최악의 경우도 다시 계산이 1,856번에서 137번으로 줄었다(2,000틱).
- 처치 처리 중 예외가 나면 사건이 닫히지 않는다. 사건은 한 번에 끝나므로 실행이 끝난 직후(마이크로태스크) 열린 채면 닫고 알린다.

### 지키는 검사

`scripts/smoke-player-stat-cache.js` 하나에 핵심만 둔다(스모크를 핵심 20개 이하로 줄일 때 둘을 합쳤다, 2026-10-08):

1. 정적 검사: 계산 본체가 닿는 함수(389개)는 시계를 직접 읽지 않고, game에서는 빌드 입력과 맥락 필드만 읽고,
   `PLAYER_STAT_DERIVED_WRITES`만 쓰고, 모듈 상태와 바뀌는 전역 변수는 이유가 적힌 것(`MODULE_STATE`)만 읽는다. `window.함수`로
   부르는 것도 따라간다. 틱이 읽는 필드를 다른 이름의 객체로 읽어도 걸린다. 실패 메시지가 새 값을 어디에 선언해야 하는지 알려 준다.
   모든 구역 객체와 맥락 값이 작게 JSON으로 바뀐다.
2. 정산: 캐시로 답한 호출마다 새로 계산한 값과 같고(시작 전사, 전사 키스톤), 넘겨준 계산은 바뀌지 않고, 계산이 객체 안쪽에서
   읽는 값도 서명이나 맥락 목록이 덮는다(모양만 다듬는 ensure, normalize 함수는 뺀다). 적중률 하한 90%. 캐시를 끈 정산과 끝이 같다.
3. 평소 플레이: 입력 없이 코드로 바꾼 편집 11가지(패시브, 장비 교체와 제자리 수정, 보조 젬 레벨, 사용 스킬, 재능 카드, 그루터기,
   레벨, 무기 숙련, 구역, 시련)를 다음 계산이 바로 알아채고, 무효화 함수와 사건 괄호가 세대를 바꾸고, 캐시가 볼 수 없는 표 수정은
   자체 점검이 한 주기 안에 고치고, 손으로 켠 백그라운드 표시는 매번 계산하고, 예외로 열린 사건은 실행이 끝난 직후 닫힌다.

`tests/browser/player-stat-cache.spec.js` (실제 브라우저): 실제 게임 틱, 인벤토리에서 투구 장착, 패시브 노드 클릭, UI용 능력치
요청을 거치는 동안 캐시 답이 모두 새 계산과 같고, 키 입력이 캐시를 버린다.

일부러 넣은 버그 두 개(본체에서 생명력을 직접 읽기, 생명력 변화를 무시하는 캐시 비교)를 각각 정적 검사와 그림자 비교가 잡는 것을
확인했다.
