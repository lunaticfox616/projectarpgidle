# 캐릭터 총 스탯 계산 계약

`getPlayerStats(includeBreakdowns)`가 전투와 UI에 제공하는 총 스탯의 진입점이다.
장비 비교·실시간 전투·방치 재생이 같은 계산을 사용한다. `false`는 수치만,
`true`는 같은 수치에 툴팁 설명을 추가한다. 저장 형식이나 밸런스는 바꾸지 않는다.

## 계산 순서와 책임

1. `combat.js`: 별 쐐기 등 기존 파생 상태 갱신, 장비·생장판 입력 해석.
2. `combat-build-stats.js`: 장비 출처별 합산. 장비 기본/명시 옵션 버킷과 로컬 방어를 분리한다.
3. `combat.js`: 주얼·고유 효과·일반 패시브 등 기존 변환. 이어서 `combat-build-stats.js`의
   루프 패시브 → 전직 노드 합산을 호출한다.
4. 액트 보상 → 루프·심화 투자 → 영구 보너스 → 지하계 룬 → 기타 성장 출처 순서로 합산한다.
   루프 투자와 룬의 합산 책임은 `combat-build-stats.js`에 있다.
5. `combat.js`: 보조 젬 계산. 자신의 스탯에 비례하는 보조 젬은 보조 젬을 제외한 출처를 읽는다.
6. 성소·별자리·실시간 버프·재능·속성 변환·플라스크와 최종 방어/공격 계산을 기존 순서로 수행한다.
7. 총 스탯 결과에 재능 후처리와 소환 DPS를 반영하고, 요청한 경우만 설명을 조립한다.

출처별 버킷을 하나로 일찍 합치면 로컬 방어·배율·출처 표시가 달라질 수 있다.
`sumNonSupportStat`과 `sumStatAcrossBuckets`의 포함 출처도 같지 않다.
합산 순서, 내림 시점, 상한 적용 순서는 게임 규칙이며 구조 정리만을 위해 변경하지 않는다.

## 상태와 재사용 범위

- 합산 함수는 호출자가 소유한 출력 버킷만 수정한다. 투자·노드·룬 입력을 변경하지 않는다.
- 총 스탯 진입점 전체는 아직 순수 함수가 아니다. 기존 별 쐐기 파생 상태, 만료 버프,
  대상 디버프 정리 등이 있다. 호출이 완전한 읽기 전용이라고 가정하지 않는다.
- 기존 방치 장비 캐시는 유지한다. 캐시 버킷은 평가마다 `Object.create`로 분리하고 변환 결과가
  원본으로 새지 않게 한다. 상속된 필드가 있으므로 버킷을 임의 열거해서 합산하지 않는다.
- 소환 DPS는 **한 번의 동기 평가 안에서만** 이름·젬 레벨이 같은 기대 타격 결과를 재사용한다.
  대상·플레이어 스탯·시간은 이 평가에 공통이다. 다음 호출에는 새 Map을 사용한다.
  같은 피해를 소환수 수만큼 더하는 순서는 유지한다. 실제 공격 판정/난수에는 사용하지 않는다.
- 소환 설명은 수치 계산 뒤 별도 함수에서 생성한다. 설명의 기존 표기식도 보존한다.
- 총 결과를 장기 캐시하지 않는다. HP/ES·버프 만료·적 저항·젬 강화·장비 비교·방치 스냅샷 교체를
  모두 포괄하는 갱신 계약 없이 장기 캐시를 추가하면 오래된 값으로 싸우거나 보상을 계산할 수 있다.

## 검증과 측정

```powershell
node scripts/smoke-offline-stat-results.js
node scripts/smoke-combat-calculation-contracts.js
node scripts/benchmark-player-stats.js 85254d7a881090da430cac5dda68e13082fc74a3
npm test
npm run check:architecture
```

벤치마크는 지정 리비전의 `getPlayerStats`, `estimateSummonDps`, `getGemBonusSources`를 현재 작업본에 교체해서
비교하므로 다른 작업 변경의 영향을 줄인다. 초반/후반·루프 투자·룬·저체력·보스·저항 변경·
버프 만료·장비 해제·젬 보상·소환 금지·선택 데이터 누락에서 전체 결과와 상태를 비교한다.
후반 부하 세팅은 실제 저장이 아닌 100레벨, 패시브 100개, 생장판 32개, 소환수 8기의 합성 세팅이다.

2026-09-09 1차 책임 분리만으로는 후반 수치 계산이 약 4.92ms로 전후 차이가 작았다.
이후 구간별 호출을 계측해 젬 레벨 입력의 반복 탐색이 큰 비중을 차지함을 확인했다.

## 젬 입력 공유와 HUD 스탯 전달

`skills.js`의 `createGemBonusEvaluation`은 한 번의 동기 계산에 필요한 젬 레벨 입력을 만든다.
이미 해석한 장비에서 관련 옵션만 재귀 순서대로 추출하고, 패시브 효과도 한 번 조회한다.
옵션을 한 덩어리로 합산하지 않고 장비별 묶음을 유지해 소수점 덧셈 순서를 보존한다.
같은 태그 조합의 기본 젬 보너스는 이 입력 객체 안에서만 재사용한다.

`getPlayerStats`가 보조 젬 계산 직전에 만든 입력을 주 공격·보조 젬·상호 보완의 대표 소환수·
최종 소환 DPS까지 명시적인 인자로 전달한다. 다음 총 스탯 조회에서는 새 입력을 만든다.
주얼·전직·재능의 대상별 추가 효과는 계속 별도로 계산하며, 저장 데이터와 총 스탯 반환 객체에
이 입력을 넣지 않는다. 방치 재생은 기존 빌드 메모를 사용한다.

HUD의 지속 피해 예고 게이지는 `updateCombatUI(pStats)`로 전달받은 스탯을 그대로 사용한다.
보조 젬 장착 시 공명력 확인도 앞서 계산한 스탯을 재사용한다. 이전 툴팁 값이나 새 총 스탯 조회를
이 경로에 끼워 넣지 않는다. 장착 한도 정리로 실제 세팅이 바뀐 경우의 재계산은 유지한다.

입력 공유 후 Node VM 측정(5회 중앙값, 회당 60조회):

| 합성 세팅 | 이전 | 이후 |
| --- | ---: | ---: |
| 후반 수치 전용 | 4.85ms | 1.73ms |
| 후반 설명 포함 | 6.33ms | 2.26ms |
| 초반 수치 전용 | 0.320ms | 0.335ms |

후반에서는 약 64% 감소했다. 초반에는 개선이 없으며 작은 입력 준비 비용이 추가된다.
장비 해석 호출은 총 스탯 조회당 132→44회, 패시브 효과 조회는 900→200회로 줄었다.
실제 브라우저 전체 프레임 시간이나 모바일 발열이 같은 비율로 줄었다는 뜻은 아니다.
원시 시간은 `artifacts/player-stats/benchmark.json`, 진단 호출 횟수는
`node scripts/profile-player-stats.js <측정명>`의 출력에 저장한다.
진단 래퍼의 시간에는 계측 비용이 포함되며, 중첩 함수의 시간을 서로 더하지 않는다.

## 장비 툴팁 비교

PC 인벤토리와 장착 슬롯의 마우스 호버는 장비 설명을 즉시 표시한다. 비교 계산은 첫 렌더 기회 뒤
idle callback(미지원 환경에서는 타이머)으로 슬롯 하나씩 처리한다. 기존 100ms 고정 대기는 제거했다.
각 슬롯의 교체 전·후 수치는 같은 동기 작업 안에서 `getUiPlayerStats({}, false)`로 계산한다.
이전 툴팁 스탯이나 오래 보관한 비교 HTML을 재사용하지 않는다. 수치 비교에는 설명 생성이 필요 없다.

다른 대상 호버·포인터 이탈·클릭·드래그 시 예약 작업을 취소하고, 늦게 실행된 콜백도 작업 식별자로
차단한다. 클릭 상세 창의 비교 작업은 호버 이탈로 취소하지 않는다. 모바일은 터치 상세 창을 유지한다.
회귀 검사는 실제 계산 결과, 슬롯 복원, 입력 읽기 실패, 빠른 대상 교체, 터치·더블클릭을 확인한다.

현재 총 계산 함수에는 고유 아이템·재능·최종식 결합이 여전히 남는다. 이후 분리도 출처/변환 단계별로
진행하고 위 동등성 비교를 유지한다. 추가 성능 작업은 실제 브라우저 프로파일에서 비중이 큰 구간을
먼저 측정한다. 무제한 결과 캐시나 임의의 갱신 지연을 추가하지 않는다.

## 장비 일괄 분석의 비교 조건

`equipmentTriage`는 시작 시 전체 게임 상태와 전투 시각을 캡처한다. 기준 수치와 각 후보 슬롯은
동일한 원본 스냅샷의 새 복사본에서 `getPlayerStats(false)`로 계산한다. 계산 함수가 파생 상태를
정규화하거나 상태이상을 해제해도 다음 후보 및 실제 게임에는 전파되지 않는다. 전역 `game` 교체는
동기 계산 안에서만 일어나고 `finally`에서 원래 객체를 복원한다. 저장 형식과 로드 순서는 바꾸지 않는다.

인벤토리는 별도로 한 번 복사해 재귀적으로 동결하고 계산 간 공유한다. 스탯 계산의 인벤토리 접근은
읽기 전용이며, 오래된 상자 주얼의 보유 장비 등급 보너스에도 원래 목록을 그대로 제공한다.
매 슬롯마다 수백 개 아이템을 다시 역직렬화하지 않는다. 장착 후보 자체는 별도 복사한다.

분석 무효화 입력은 같은 모듈의 `BUILD_FIELDS`/`BUILD_PARTS`가 소유한다. 장비, 공격·보조·컨디션 젬,
패시브, 재능, 각인, 큐브, 생장판, 룬, 심화 투자 등 세팅 변경을 감지한다. 새 성장 시스템을 추가하면
입력 목록과 행동 검사를 함께 확장한다. 전투 시각·생명력·버프 만료, 단순 경험치 누적, 장비 잠금은
무효화 사유가 아니다. 표시 갱신은 최대 0.5초 간격으로 확인하며 완료·필터 선택·추천 교체 전에는
즉시 검증한다. 전투 상황이 바뀐 뒤의 평가를 원하면 다시 분석한다.

중단은 타이머와 부분 결과를 버린다. 각 콜백은 예약 당시 작업 번호를 캡처하므로 중단 후 재시작한
분석을 진행하거나 덮어쓸 수 없다. 후보 오류도 부분 추천을 공개하지 않고 재시도 상태로 끝낸다.

`node scripts/benchmark-equipment-triage.js 85254d7a881090da430cac5dda68e13082fc74a3`으로
같은 최신 스탯 계산기를 사용하는 이전 분석 방식과 비교했다. 합성 후반 세팅(100 패시브, 가득 찬
생장판, 소환수 8기)의 장비 120개에서 5회 중앙값은 약 511→563ms였다. 120개 점수는 모두 같았다.
수치 전용 계산은 설명 생성을 생략하지만 상태 격리 비용 때문에 전체 CPU 시간은 약 10% 늘었다.
이 변경을 대폭적인 속도 향상으로 해석하지 않는다. 측정에는 브라우저 타이머 대기·렌더링이 제외되어
있고 실제 모바일 성능은 별도 측정이 필요하다. 결과는 `artifacts/player-stats/equipment-triage.json`에
저장한다. 회귀 검사는 버프 만료를 끼워 넣은 배치, 세팅 변경, 중단·재시작, 잘못된 후보 입력의 복원과
PC·모바일 분석 버튼 조작을 검증한다.

`node scripts/benchmark-equipment-triage-browser.js`는 저장이 분리된 데스크톱 Chromium에서 같은
후반 부하의 장비 120개를 실제 타이머와 도구 모음 렌더링을 포함해 측정한다. 5회 결과는
0.87~1.46초, 중앙값 1.17초였다(`artifacts/player-stats/equipment-triage-browser.json`).
이는 해당 개발 PC의 합성 캐릭터 측정이며 실사용 저장이나 휴대폰 성능을 대신하지 않는다.
