# 전체 구조 점검과 개선 기록

2026-09-08 기준. 모바일 화면 재설계와 함께 진행하는 구조 검토이며 전체 리뷰 완료 보고서가 아니다.
파일 수나 lint 통과를 게임 전체의 정확성·성능 검증으로 해석하지 않는다.

## 현재 실행 경로

- `index.html`은 classic script를 순서대로 로드한다. 번들러의 import 그래프가 아니라
  데이터 정의, 브라우저 전역, 함수 호출 및 부트스트랩 시점이 실행 계약이다.
- `main.js`가 100ms 타이머에서 `runForegroundCombat`을 실행하고, 보류된 정적 UI 갱신을
  최대 1.2초 간격으로 처리한다. 전투 HUD는 같은 타이머에서 별도로 갱신한다.
- `ui.js`의 `gameLoop`는 requestAnimationFrame으로 캔버스 표현을 이어간다.
  전투 시간 진행과 표시 프레임을 동일한 타이머로 합치면 게임 진행 속도가 바뀔 수 있다.
- 저장·복원 경계는 `save.js`/`save-migrations.js`, 방치 재생은
  `combat-clock.js`/`combat-replay.js`와 진행 오케스트레이션에 걸쳐 있다.
  이번 구조 검토에서 저장 및 보상 계약 전체를 새로 검증한 것은 아니다.

## 확인한 결합과 조치

| 관찰한 구조 | 영향 | 조치/상태 |
| --- | --- | --- |
| `ui.js` 약 16,300줄, `combat.js` 약 12,800줄, `passives.js` 약 12,200줄 | 렌더·진행·계산 책임을 파일명만으로 판단하기 어려움 | 수정하는 경계부터 실제 책임을 분리. 전체 파일을 기계적으로 나누지 않음 |
| `renderTalentTab`이 재능 효과 규칙 파일에 함께 존재 | 도메인 수정과 화면 변경의 경계가 불명확 | 재능 표시를 `talent-ui.js`/`talent-mobile-ui.js`로 이동. 슬롯 변경 후 기존 UI 갱신 경로 사용 |
| `performUpdateStaticUI`가 숨겨진 관리 패널도 생성 | 닫힌 거래소·전문화·플라스크의 반복 작업 | 표시 중인 패널만 렌더. 거래소 시간에 따른 재고 갱신은 별도 유지 |
| `updateCombatUI`가 숨겨진 캐릭터 능력치도 매번 작성 | 100ms 전투 HUD 갱신에 상세 시트 비용이 결합 | `character-stats-ui.js`로 분리, 캐릭터창이 표시될 때만 갱신 |
| `setTextById`가 동일 값도 매번 작성 | 불필요한 텍스트 노드 변경 | 기존 공용 함수에서 동일 textContent를 비교하고 변경 시에만 작성 |
| `updateCombatUI`의 레벨·경험치·지역 비교가 `innerText`를 읽음 | 직전 게이지 스타일 변경 뒤 강제 레이아웃 가능 | 기존 `setTextById`로 통합. ES·귀환 문구도 동일 값 반복 쓰기를 제거. PC·모바일에서 표시 갱신, 동일 텍스트 노드 유지와 innerText 읽기 0회 검증 |
| `updateCombatUI`가 `game.playerHp`를 회복 상한으로 직접 제한 | 화면 갱신과 전투 상태 변경의 결합 | 상한 적용을 공통 `prepareCombatTick`으로 이동. HUD 반복·오래된 스탯으로 HP가 변하지 않음, 실제 전투/방치 준비의 초과 회복·사망 유지·전사 50% 상한 검사 |
| 모바일 메뉴가 `div` 클릭과 전역 Escape에 의존 | 키보드 선택 불가, 초점 이탈, 열린 메뉴의 aria-hidden 갱신 오류 | 메뉴의 키보드 경계·초점 복원·버튼 역할을 모바일 수명에 맞게 관리 |
| 전문가 getter가 `ensureExpertiseState`를 반복 호출 | 조회 중 정규화·해금 기록 순회가 중첩됨 | 코드에서 확인. 전체 프레임 병목으로 확정하지 않았으며 변경하지 않음 |
| 플라스크 선택 창이 정적 UI 갱신 함수 내부에서 모든 계열의 선택 카드를 조립 | 모바일 탐색 길이와 큰 함수의 결합 증가 | `flask-ui.js`가 슬롯 탐색 및 공용 선택 카드 조립을 소유. 모바일은 선택한 계열 5단계만 생성하고 PC는 전체 유지. 발견·레벨·동일 계열 제한은 기존 도메인과 연결 |

시트 분리는 공격·방어·상태이상·조건부 수치·특수 설명으로 책임을 나눴다.
계산식과 값의 보정은 기존 동작을 유지한다. 새 저장 필드는 추가하지 않았다.
캐릭터 모듈은 UI 계층에서만 사용하고 데이터·전투 계산이 호출하지 않는다.

## 실제 실행 관찰

주얼 제작 화면 조립을 `jewel-crafting-ui.js`로 분리하고 화면 선택은 UI 모듈의 런타임 상태로
관리한다. 재화 사용·융합·증폭 규칙은 기존 도메인을 호출한다. 증폭합성 비용 검사가 기본 비용과
추가 비용을 따로 검사해 재화가 음수가 되던 경계는 총비용 검증/단일 차감으로 수정했다.
기존 융합 도메인이 증폭 체크를 DOM에서 읽는 역방향 의존은 남아 있으며 별도 구조 개선 대상이다.
주얼 융합과 공허 제작창의 재료 선택은 칸 번호 대신 주얼 객체 참조로 보관하도록 수정했다.
저장되지 않는 기존 임시 선택 상태이며, 소비자는 기존 getter로 현재 인벤토리 위치를 받는다.
장착 교환·목록 재정렬 뒤 다른 주얼이 선택되던 문제를 제거했고, UI의 선택 정규화 쓰기도 없앴다.
`smoke-crafting-target-stability.js`와 `jewel-selection-stability.spec.js`에서 앞 항목 장착,
선택 주얼과 장착 슬롯 교환, 재정렬 후 실제 융합, 공허 제작 재료 이탈 시 무차감을 검증한다.
확인창을 연 뒤 옵션 자체나 전체 선택을 바꾸는 경우의 미리보기 스냅샷 계약은 추가 검토 대상이다.

`artifacts/profile-live-combat.cjs`는 PC Chromium의 모바일 뷰포트(412×915)에서 측정한다.
장비 12개·패시브 100개·생장 아이템 32개·소환수 8개인 합성 상태이며 합법적인 빌드나
실제 사용자 저장으로 가정하지 않는다. 적 12마리(보스 포함)의 체력을 높여 6초간 전투를 유지한다.
안내 창이 끼어든 첫 실행은 지속 전투 근거에서 제외했다.

수정 전/후 모두 마지막에 적 12마리·소환수 8개가 살아 있고 전투 중단 및 pageerror가 없었다.
requestAnimationFrame 간격의 95백분위는 16.8/16.7ms였다. 이 단발 측정으로 프레임 개선률이나
휴대폰 발열 감소를 주장하지 않는다. CPU 샘플에서 캔버스 작업, HUD 작성, 스탯 계산이 관찰됐다.
그래픽 드라이버/GPU 비용은 JavaScript 샘플만으로 확정할 수 없다.

회귀 검사 `character-rendering.spec.js`는 닫힌 시트의 값·텍스트 노드 불변,
열린 시트에 최신 값 반영, 동일 값 반복 시 노드 불변을 PC·모바일에서 직접 확인한다.
이번 분리 검증: `npm test` 175/175, `npm run check:architecture` 통과.
캐릭터 표시·분류 전환·모바일 전투 배치 브라우저 검사 5개 통과(모바일 전용 PC 검사 1개 제외).

## 남은 전체 검토 범위

### 30초 Android 설정 재현 측정의 범위

`artifacts/profile-android-combat.cjs`는 Android UA, 412×915, DPR 2.625를 사용한다.
기존 짧은 측정은 모바일 터치/크기만 설정해 UA 기반 30fps·렌더 배율 1.5 제한을 검증하지 못했다.
새 측정에서 실제 캔버스 clearRect 간격, 종료 시 적/소환수/전투 중단 여부, CPU 샘플과 GC 전후
메모리를 수집한다. 합성 세팅이며 실기기 성능 측정은 아니다.

기본 headless Chromium의 SystemInfo는 SwiftShader 소프트웨어 렌더러였다.
기본 공격 이미지의 `restore` 비용이 컸지만 상위 필터를 제거하는 실험은 유의미한 개선을 보이지
않아 생산 코드에서 되돌렸다. 이 결과로 게임 이펙트 품질이나 공격 빈도를 낮추지 않았다.
측정기는 `gpu` 인자로 D3D11을 사용할 수 있고 결과에 실제 렌더러를 기록한다.
`android-combat-hardware-current.json`은 RTX 5060 Ti / D3D11 사용을 확인했다.
30초 TaskDuration은 약 2.4초, ScriptDuration은 약 1.2초였다. 소프트웨어 렌더러의
약 24초 TaskDuration과 차이는 측정 환경 차이이며 게임 수정의 개선률이 아니다.
실제 그리기는 806회, 간격 95백분위 약 50.1ms로 목표 33.3ms보다 불규칙했다.
`gameLoop`가 RAF 제공 타임스탬프 대신 콜백 실행 시점의 `performance.now()`를 사용해,
다른 작업으로 늦어진 콜백 다음의 정상 프레임까지 건너뛰는 문제가 있었다. RAF 타임스탬프를
사용하도록 수정했으며 프레임 제한 값은 유지한다. 같은 D3D11 합성 측정의
`android-combat-raf-clock.json`에서는 30초 903회, 간격 95백분위 34.2ms, 최대 36.2ms였다.
실기기 수치는 아니며 30fps를 복원하면서 그리기 횟수는 증가하므로 발열 감소로 해석하지 않는다.
`battle-frame-clock.spec.js`는 60/120Hz 프레임 시각에 콜백 지연을 섞어도 PC·모바일의 기존
제한 주기를 지키는지 실제 캔버스 그리기로 확인하고, HP·경험치·지역·진행도·처치 수 불변을 검사한다.

HUD 단독 100회 갱신은 innerText 읽기 300→0회, 합계 14.7→8.9ms,
95백분위 0.3→0.2ms였다(`artifacts/hud-before.json`, `hud-after.json`). 단발 PC 합성 측정이다.
30초 소프트웨어 렌더링 전투의 paint 간격 95백분위는 전후 모두 약 49.8ms였으므로,
HUD 수정으로 전체 프레임 성능 또는 발열이 개선됐다고 주장하지 않는다.
GC 후 사용 힙은 시작 약 9.9MB→종료 약 13.1MB였다. 초기 캐시·로그 생성이 포함되어
이 짧은 구간만으로 누수나 장시간 안정성을 판정할 수 없다.

1. 모바일 각 콘텐츠의 대표 데이터·터치·스크롤·키보드 흐름: `mobile-redesign.md`의 범위 유지.
2. 전투/렌더 경계: 일반·보스·효과 밀집·장시간 실행 및 CPU/GPU/메모리 분리 측정.
3. 스탯 계산: 장비·젬·패시브·소환 및 조건부 효과의 무효화·캐시 계약 점검.
4. 저장·복원·방치: 손상/이전 저장, 백그라운드 전환, 정산 중단·재개, 중복 보상 방지 추적.
5. 진행과 콘텐츠: 해금·루프 전환·영구 투자·재화 소비의 경계 및 실패 시 부분 변경 검토.
6. UI 갱신: 창 수명·이벤트 중복·초점·입력 중 갱신, 화면이 닫힌 경우 타이머/DOM 정리.
7. 네트워크·인증·앱 수명: 로그인·동기화 실패, 재시도, 모바일 복귀 경로 검토.

전체 검토 완료는 각 경로의 코드 추적과 대표 행동·실패 검증 후 판단한다.
